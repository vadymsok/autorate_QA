# План тестування вебсервісу «АвтоРейт» (Спринт 2)

## 1. Продукт і межі тестування

**Об'єкт тестування:**  
Вебсервіс «АвтоРейт» (публічний каталог і рейтинг автомобілів на базі Buggy Cars Rating: https://buggy.justtestit.org/) та розрахунковий бекенд-модуль бізнес-логіки на Java.
* Архітектура та стек: клієнтська частина Web SPA (Angular/HTML5/REST), серверне REST API навчального стенду Buggy, а також модуль перевірки та агрегації бізнес-логіки на Java 17 (JUnit 5, Maven) із класами `RatingAggregator`, `VoteValidator`, `ModelSearch`.

**Межі тестування (In Scope):**
* Модуль автентифікації та реєстрації користувачів через вебінтерфейс (валідація логіна, складність пароля, успішний вхід).
* Модуль голосування за моделі автомобілів: клієнтське віддання голосу за модель (сторінка моделі на demo), а також ізольована валідація голосів і коментарів у класі `VoteValidator`.
* Алгоритми підрахунку та агрегації рейтингу: розрахунок середнього бала та «Рейтингу тижня» у класі `RatingAggregator` (зважені оцінки за репутацією, тай-брейк за алфавітом).
* Каталог та пошук автомобілів за маркою та моделлю (вебкаталог та клас `ModelSearch`).
* Нефункціональні характеристики: продуктивність інтерфейсу під час завантаження списків моделей, стабільність роботи в різних вебпереглядачах.

**Поза межами тестування (Out of Scope):**
* Внутрішня хмарна інфраструктура хостингу AWS / Heroku навчального сервісу Buggy Cars Rating.
* Сторонні сервіси автентифікації та зовнішні CDN бібліотек.

## 3. Інструменти, середовище та тестові дані

* **Браузери для тестування UI:** Google Chrome (актуальна стабільна версія), Mozilla Firefox, Microsoft Edge.
* **Середовище та інструменти виконання тестів Java-модуля:** Java Development Kit (JDK 17), Apache Maven, тестовий фреймворк JUnit 5, Mockito.
* **Аналіз трафіку та інтерфейсу:** Chrome DevTools (вкладки Elements, Console, Network, Application).
* **Тестове середовище:** публічний стенд https://buggy.justtestit.org/.
* **Тестові дані та облікові записи:**
  * Гість (неавторизований відвідувач для перевірки обмеження доступу до голосування).
  * Зареєстрований користувач для тестів: логін створюється під час тест-сесії через форму реєстрації (або використовується валідний створений акаунт, наприклад `test_user_qa` / `Password123!`).
  * Тестові автомобілі стенду: модель з високим рейтингом (Lamborghini Diablo), моделі без голосів для перевірки первинного зарахування.
  * Тестові датасети для модульних перевірок: синтетичні масиви об'єктів оцінок для класу `RatingAggregator` у JUnit-тестах.

## 4. Ризики та припущення

### Ризики
1. **Ризик:** Недоступність або нестабільність стороннього публічного стенду Buggy Cars Rating під час проведення демо.  
   * **Захід зі зниження:** Попередній запис проходження ключових сценаріїв на відео або локальна готовність запуску тестів Java-модуля в середовищі розробки.
2. **Ризик:** Блокування IP-адреси через часті запити під час навантажувальних перевірок.  
   * **Захід зі зниження:** Обмеження навантажувальних тестів до 10–15 паралельних потоків, відмова від стресових та DoS-сценаріїв на публічному стенді.
3. **Ризик:** Наявність дефектів у сторонньому інтерфейсі Buggy, які неможливо виправити на клієнті.  
   * **Захід зі зниження:** Чітка фіксація відомих багів стороннього стенду в баг-репортах з ізоляцією від власної бізнес-логіки.

### Припущення
1. Публічний сервіс Buggy Cars Rating зберігає працездатність та консистентність бази даних протягом занять і демо.
2. Бізнес-логіка розрахунку зваженого рейтингу та розширених правил (оцінки 1..5, репутація) реалізується та тестується ізольовано в рамках Java-модуля за вимогами розділу BL специфікації SRS.
3. Усі члени команди використовують сумісне середовище розробки: Java 17 та Maven для запуску тестів.
